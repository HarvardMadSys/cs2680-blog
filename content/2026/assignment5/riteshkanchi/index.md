There were a lot of things I learned throughout this course, and I think that the assignments as a whole can be encapsulated or characterized as a "balancing act" of constraints, which varied and changed throughout the course. Certain constraints forced me to make specific trade-offs, whereas others provided more freedom to explore and experiment.

These constraints often included:

- Cost
- Time
- Solvability
- Models
- Engine
- Hardware

And each of these constraints had different effects on what was built and how it was built. In the following lessons, I go through a few of the things I learned, categorized by the constraints that I had to work with.

## Scaffolding agent understanding and knowledge

Assignment 2 was the assignment where I definitely felt the most constrained, both by my knowledge of coding harnesses and the capabilities of the models I was using. At some times during the assignment, it felt as if the model was really good, and in others, it felt like the model was really bad. Throughout my test runs, I kept noticing a similar pattern: when the harness was provided with the necessary context to solve the problem, it was able to do so effectively --- this seems like a fairly obvious statement, but it was something that I had not considered before. This led me to two harness design decisions:

### RepoMap

RepoMap is a map of the repository given to the harness, which allows it to determine which files to operate on, and which files to ignore. It pulls backticked terms and code-looking terms from the task and uses them to find the relevant files in the repository. Then, it checks the interface and source files to find relevant methods to operate on, provided into the initial prompt. This was a very important addition to the harness, as it allowed the harness to focus on the relevant files, rather than wasting time and resources on irrelevant files. In assignment 2, when working on fixing the React Compiler's manual memoization, the harness kept guarding the wrong location and only patching `FinishMemoize` not `validateInferredDep`. One thing I noticed was that the post-edit test suite results were not always indicative of whether the harness had effectively solved the issue; the post-edit test suite results kept returning 1718/1718 tests passing, even when the harness was not guarding the right location.

This was a bit of a surprise to me, as I had assumed that the test suite would be a good indicator of whether the harness had effectively solved the issue. Adding RepoMap allowed the harness to find the right methods to operate on, such that `validateInferredDep` was patched with the proper guard. Previously, it kept creating new methods rather than using the existing methods; this is part of what led to the wrong guard. Additionally, I added a "zero-tests" rule, to not wholly rely on the post-edit test suite results. This, paired with RepoDocs (described below), allowed the harness to find the right methods to operate on, and to patch them with the proper guards, while following the right testing directions. At one point, I tried bundling `ctags` as an additional tool to help the harness find the right methods to operate on, but this was not as effective; I thought about using it as a way to help the model do continuous searching throughout the codebase, but found it to be a fairly unhelpful addition, as the harness never really utilized it.

### RepoDocs

RepoDocs looks for `AGENTS.md` and `CLAUDE.md` files that are present in the repository, and uses them to provide additional context to the harness. Given that more and more repositories are using these files to provide agents with standardized information about how to operate on the repository, this felt like a very timely addition to the harness. It provides the needed information as specified by the codebase maintainers. Similarly, in the React Compiler, there was a bug with the memo cache having stale imports. On initial runs, the harness spent a significant amount of time (around 71 to 75 turns) re-reading files it had already found and figuring out how to run the tests. Adding RepoDocs gave the harness information on how to run the tests much earlier, as the testing instructions were specified in `CLAUDE.md` explicitly. This, along with RepoMap, enabled the harness to begin editing as soon as turn 30 to 42 rather than turn 71 to 75. With these fixes, the stale import bug was fixed, due to the pre-existing knowledge of how the codebase was situated.

## Time versus cost

In assignments 2 and 3, it felt like the primary constraint was first cost, and then time when trying to reach a solution. This changed in assignments 4 and 5, where the primary constraint was no longer cost, but only time. When it came to hosting and serving our own models, and cost no longer a factor, it felt like I could explore more and try different things, rather than being limited by the cost of the models I was using (expert models, for example, in A3 were something I did not use significantly). If anything, I spent a lot of time on assignments 2 and 3, compared to assignments 4 and 5, since these constraints shifted. Task solvability was always a high-level constraint, but the time and cost constraints were more immediate and pressing. For example, in assignment 3, I added a turn budget and primarily relied on the standard model for model calls (and using the expert model sparingly for failing diagnoses). Similarly, I only used reasoning on the first and on critical turns, helping both time and cost.

But with assignment 4 and 5, I spent less time thinking about reducing cost, and rather thought about how to support my harness via the serving engine. The most notable in assignment 4 being the use of the hierarchical cache to expand the KV cache, resulting in a 93% cache hit rate (up from 41% on earlier engine versions). In assignment 5, I went further by introducing speculative decoding (something I tried on assignment 4, but couldn't figure out) and expanding the max running requests to 16, which enabled more tasks to be running at once, and faster---the decoding process drafted 3 tokens ahead and verified 4 tokens per step. In Assignment 5, I removed the aforementioned turn budget, and instead told the agent how long it had been working and provided a 35-minute time limit. When cost is involved, I found the need for these turn budgets, but since I was serving the model myself, this was no longer a constraint. Rather than focus on hyperoptimizing the harness in general, modifying the engine specifically around supporting the harness was the right direction towards this time optimization (this was my main takeaway of assignments 4 and 5).

## keep it simple, stupid (or not?)

As I worked towards assignments 3, 4, and 5, I couldn't help (and still feel) as if there are poor returns on making agent harnesses overly complex. When provided with too much context, the model may overfit to the context, and not be able to generalize well to new situations. In contrast, when provided with too little context, the model may not have enough information to make informed decisions, and may make poor decisions as a result. Both of these, evidently, are not ideal.

So obviously, you can draw the conclusion that the right amount of context and flexibility is in the middle of these: providing _enough_ foundational scaffolding and tooling to enable the harness to operate effectively, but not so much that the model is overfitting to the context. At the end of assignment 2, I had felt that my agent was overly complex. Assignment 3 was a bit of a course correction towards simplicity, but only near the end. With every poor leaderboard submission, I added new levels of complexity, in the hopes of finding a "silver bullet": multi-agent systems, graders and reviewers, and using the small model as a tool. As I kept introducing these features across runs, I observed that solves on tasks I had previously solved with seemingly _less_ were becoming unsolved, seeing worse and sporadic performance of my harness: a 4/26 run, many 7/26s and 8/26s, and a few 10/26s. This went against my initial intuition, where adding more features would improve performance. While running tests locally was helpful, macOS x86-64/ARM translation made it an unreliable indicator of time and cost spend --- which were core components of the assignment. This led me to rerun one of my earlier harnesses, before these features ballooned, and to deliberately test each component rather than throwing everything at the wall and seeing what stuck. After significant backtracking, that harness reached 14/26, which was the best I had gotten. Was this the right takeaway? Was it just luck? Rerunning the same harness gave 9/26, so the variance was large (model degradation, perhaps?).

That's all to say, by assignment 4 and 5 --- while I don't feel I have the _perfect_ agent harness solution yet --- I feel that I have a better understanding of the trade-offs between complexity and simplicity; and I feel like this is maybe the right lesson. When looking at existing, successful harness architectures online (e.g., [Hermes](https://hermes-agent.nousresearch.com), [Kimi Code](https://www.kimi.com/code/en), [Claude Code](https://claude.com/product/claude-code)), the majority of them were fairly simple in terms of scaffolding, placing greater emphasis on the model to do the heavy lifting. So, given that we were designing a harness around off-the-shelf models compared to state-of-the-art models (which are often designed in tandem with their harnesses), do the same ideas apply? In this regard, I am unsure --- a weaker model may rely or need more scaffolding and tooling to operate effectively, whereas a stronger model may not need as much scaffolding and tooling to operate effectively (as seen with aforementioned harnesses). Maybe this is an open question for the future, especially when we consider the increasingly capable on-device and open-source models that are being developed. The intermingling of model, engine, agent, and harness all play a role in the overall effectiveness of the system, and I think that this is something that will be explored more in the future, as discussed in the next section.

## A future of dedicated agent harness architectures

I feel like my biggest takeaway from this course is that I believe that the future will orient around domain-specific, dedicated agent harness architectures. A lot of our current harness solutions are general-purpose --- the tasks in the course that we tested against often required a lot of different capabilities and operated on various languages and frameworks. Especially once we got to engine serving, I began to realize that it's not only about the harness or the model of choice, but about every component of the system working in tandem. While `SKILL.md`/`AGENTS.md` are great ways to provide some of this specific knowledge to scaffold the agent and help it, the harness itself was not necessarily the best solution for every task. Similarly, while it would be great to have a harness that could parse through an entire codebase effectively, I can't imagine that this scales well to every codebase, and that there are likely better solutions for specific applications.

What does this mean for the future of harnesses? Well, for one, I think that fine-tuned models to specific languages and frameworks will begin to be the norm, such that companies will be able to provide harnesses that are specifically designed for their codebases, rather than relying on a general-purpose models that may or may not work well for their specific application. Then, the harness can be designed to work with the model, and provide tools for these codebases' specific needs.

In my own experience, using agentic harnesses with established codebases tends to be much more successful in an additive sense, rather than in the case of debugging or refactoring. With such codebases, given the greater context available, I've noticed how newly-generated code tends to be in the "flavor" of my own handwritten code for greater understanding, rather than greenfield code that lacks this foundational readability and understanding.
